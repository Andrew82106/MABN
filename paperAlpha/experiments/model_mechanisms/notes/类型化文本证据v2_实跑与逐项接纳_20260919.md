# 类型化文本证据v2：实跑与逐项接纳

## 结论与主线位置

本轮推进“运行文本 → 有原文支持的候选观测”，**没有训练或接通150参数BN，也没有新增安全检测准确率**。新版表述消除了通用polarity的歧义，但真实提取仍有分类错误和覆盖缺口；不能只看通过率宣布整体升级。

API原始响应、原整条验收、两版逐项派生分别保存。后加的逐项规则不追认原实验成功、不覆盖原结果，也没有重调API到通过。

## 1. 类型化协议

`src/paperalpha_runtime/semantic_evidence_v2.py`用19个有明确目标的predicate替代通用肯定/否定：动作请求/禁止/暂缓、授权主张、执行主张、证据可用性、数值约束、估算/数值、拒绝内容及未定。仍区分直接陈述、转述、拒绝、未定表达。

- 缺少批准记录不等于拒绝批准；未付款不等于禁止付款。
- 估算金额不等于允许支出的上限。
- 条件许可必须引用条件；数值类必须引用数值。子引用必须包含在主引用中，本地计算全局字符位置。
- 关系分为同一命题、阶段更新、冲突、相关、未知；附对象、适用时间、依据是否可比较的模型判断。
- 提议冲突但三个可比性维度不全为same时，保留原提议，同时记为`unresolved_comparison`。即使全为same，也只是`scope_matched_conflict_candidate`，不是已核实冲突。

使用[OpenAI Docs结构化输出接口](https://developers.openai.com/api/docs/guides/structured-outputs#structured-outputs-vs-json-mode)，外加本地原文验证。API仍为用户指定本地网关的5.5、low、并发2、60秒超时、无重试、无可调用工具；不改当前对话设置。v2输出上限3200，v1为2200，提示和schema也不同，不能当同预算消融。

## 3. 逐项接纳：不让局部格式失败清空整条信息

新增`semantic_observation_batch.py`和`revalidate_semantic_items.py`。先对原运行做冻结审计，再按原v2冻结校验器逐项检查已保存响应；不修复原文、补填数值、重分类或升级授权。

根对象状态不一致、超8项、无法解析或API失败仍作为整体缺失保留。合法根对象下的每一项有独立接纳/拒绝记录、原提案摘要哈希和理由。候选项共享当前记录组，不被宣布为独立证据；空结果也不表示安全。引用某个先前记录不要求该记录自己的提取成功，因为引用重新核验的是原始文本。

### 3.1 首次派生暴露了错误的去重粒度

第一版逐项接纳沿用`predicate + presentation + 主引用位置`作为身份，真实文本保留94项、拒绝38项。检查发现：24个被当重复的项包含同一句话中的不同数值或条件，例如“直接支付上限400”和“报销上限650”。主引用相同不代表命题相同。

该版本结果和源码保留于`results/semantic_v2_items_dl14_20260919/`及对应controls目录，不删除。

### 3.2 当前派生：明确子命题身份

当前`text-evidence-item-batch-v2`的身份包含：predicate、presentation、主引用位置、数值子引用位置、排序后的条件子引用位置。引用历史关系不参与身份，不能通过多加一条支持关系制造新证据。仍完全相同的身份全部排除，不按顺序挑一个。

## 4. 作者逐例检查：哪些问题仍没解决

本轮查看全部4条冲突提议、先前出错的记录及数值/暂缓案例；不是独立盲审，不计算语义准确率。

- **缺失证据**：journal-12的medical_notes查询失败现在是`evidence_claimed_missing`，没有再把请求获取资料和查询失败直接当命题矛盾。它仍关联到另一次查询失败，关系只是候选。
- **暂缓仍误分类**：journal-3的“Do not authorize payment or submit yet.”仍被标为`action_prohibited`而非暂缓。journal-50的可见历史包含该记录，但没有提出二者的阶段更新关系。不能用“旧矛盾边消失了”声称阶段变化已经识别成功。
- **条件有部分保留**：journal-50最终执行请求保留“If fit is acceptable...”条件；另有一条把含“clarification has been sent”的整句标作证据存在，是否对应正确证据对象还需审定。
- **比较依据不足**：journal-59查询缺失与先前coverage_context的3条冲突提议，都有时间更新/依据未知；journal-66金额在限额内与journal-53的over_budget提议，依据不同/时间未知。4条均被本地规则降为无法完成比较，不是LLM已正确解决冲突。
- **数值与规范的轴混在一起**：同样的“Budget Cap: $0.00”在6、15、18、21、53、56号记录被标为描述值，在31、34、37、40号记录被标为上限。文本中的“上限”与该来源是否有规范效力应分别表示；当前单一分类仍易漂移。
- **引用正确不等于类型正确**：journal-6将`active`作为reported_value的quantity_quote，字符引用检查通过，但它不是数值量。这证明原文校验无法代替语义检查。应将数值量和类别状态分开，不能简单把所有带引用的值交给预算比较器。

## 5. 对BN接入的具体影响

这些证据不能直接变成“来源恶意=1”“Agent已采纳=1”“权限已批准=1”。下一版需要落实：

1. **分离语义轴**：内容类型、数值/单位/比较方向、动作/资源对象、条件与时间、声明来源及其权威性分开。不能从一个reported_value字段同时推断金额、约束和授权。
2. **观测误差进入模型**：提取结果是带误差的观测。若建立真实主张状态及观测似然，需要独立标注来估计误差；若采用直接条件化的可学习概率因子，应如实称为条件风险模型，不宣称完成了证据真值恢复。任务最终标签不能单独保证局部状态具有期望的语义。
3. **共享来源与关联**：同记录多项和跨Agent重复转述不视为独立样本。当前记录组仅防止错误宣称独立，尚未解决跨记录共同来源识别或BN容量。
4. **时间可用性**：当前离线请求只看其时点前缀，但接入真实在线系统时提取结果会延迟到达；报警时间必须用提取完成后的实际可用时间，不能回填到原消息时刻冒充提前预警。
5. **保留完整目标**：文本接入之后，仍需角色专属知识子图、自动工作流DAG、系统层机制、独立真实标签、跨任务划分与真正MAS对照。本文不以一次提取实验代替这些工作。
