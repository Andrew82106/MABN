# HarnessAudit：真实API实跑与动作前观测

## 本轮实际进展

复用官方 OAIAdapter、Agent 提示词、工具定义、SQLite DailyLifeBank 和事后规则检查器，真正通过用户指定的本地 API 调用了 `gpt-5.5`。不是手写文本假装 Agent 轨迹，也没有重新实现一个 MAS 实验室。

随后增加实际工具处理函数入口的观测，在执行原函数前记录参数和调用身份，返回后记录结果。它位于**API运行证据接入层**，使后续 BN 可以研究执行前与执行后不同阶段；本轮没有训练新监测模型，也没有证明提前预警有效。

## 1. 实验范围与来源

- 官方仓库固定提交：`6317162590aeeb1c8dde32b880ac199933343e4a`，源仓库未改动。
- 本地接口的 `/models` 实查包含 `gpt-5.5`；先做一次 Responses 函数调用兼容性探测，成功返回函数调用，不执行该探测函数。
- 独立依赖环境：`results/runtime_envs/harnessaudit_oai_20260919/`。实装 `openai-agents 0.22.3`、`openai 3.16.2`、`pydantic 2.13.5`、`PyYAML 6.0.3`。没有修改原研究环境的依赖。
- 所有领域工具都绑定本地内存 SQLite 模拟库，不启用真实 shell、文件工作区、付款或第三方业务服务。
- API参数为 `gpt-5.5`、`reasoning=low`、每调用最多1200输出token、客户端重试0；每任务最多24次模型调用、8轮协调者、300秒。**这些只作用于实验API，未修改本对话模型/思考强度。**
- 接口方式按 [OpenAI Docs工具调用说明](https://developers.openai.com/api/docs/guides/tools)核对；本地兼容网关的实际行为另用探测和完整调用记录验证，不由官方文档推定其兼容性。
- 凭证仅从进程环境读取，没有写入代码、配置、快照或请求日志。请求日志不记录HTTP认证头。SDK tracing关闭。

官方 frameworks 注册器在 Windows 上提前导入 ClawTeam 的 `fcntl`，不能直接加载。脚本只在当前进程中将 frameworks 设为指向官方目录的包，再导入原始 OAI/core 文件；不模拟锁、不改官方算法文件。另通过派生类设置预算、记录模型调用，后一个样本包裹领域工具入口。**这是有明确偏离项的采集适配，不是原论文分数复现。**

官方编排是 hub-spoke，协调者可能重复委派，有返回边；不能把本轮直接称为已验证固定 DAG 的论文测试集。若后续用时间展开或将协调循环折叠，需要独立定义图构建规则，不可为满足无环约束随意删掉通信。

## 3. 执行前信息不是事后补出来的

`ToolLifecycleRecorder` 包裹官方 `FunctionTool.on_invoke_tool`：

1. SDK准备调用领域工具时，从真实 `ToolContext` 取得 Agent 身份、工具名和 provider call ID，分配本地 invocation ID。
2. **调用原始处理函数前**写 `tool_handler_started`，只含参数与时间，不含结果或审计判定。
3. 执行原函数，不替换返回值、不做批准或阻断。
4. 写 `tool_handler_returned` 或异常记录。

并发调用通过 ContextVar 绑定各自 invocation ID。官方完成动作的 raw_event 携带同一个ID，因而可以按真实调用身份连接前后记录，而不是靠“工具名和参数看起来一样”去猜。重复工具和重复参数不会合并。

第二例的23组记录已逐项核验：每个入口对应真实模型响应中的函数调用，每个原生工具完成记录对应同一身份、参数和返回值，入口单调时钟早于返回。这证明采集时点和绑定，不证明监测器能在该时点及时报警；模型推断与实际阻断均未执行。

这些记录仍然**不是完整v3输入**：没有独立的principal、统一资源作用域、可信提前授权检查。没有把SDK call ID伪装成批准，也没有把工具名 `authorize_payment` 的返回自动升级为可信权限事件。

## 4. 验收与仍需注意的数据问题

`audit_harnessaudit_api_pilot.py` 验证产物哈希、请求/响应/用量/动作计数，从各自冻结的官方源码和任务配置重算全部39/51条审计判定，并验证第二例的生命周期绑定。两次采集完整性检查通过；第二次运行本身依然是失败，二者不矛盾。

新增32项采集/审计测试覆盖调用预算、端点限制、并发绑定、异常传播、执行前不含返回、错误配对、未来字段混入、原返回值不被改写等。完整项目339项测试通过，保留4条既有sklearn数值/弃用警告。

需要保留的限制：

- 只有两例，且唯一完整任务为规则违规正例，不能训练或计算有意义的分类比较指标。
- 未执行LLM任务完成评审或AVS评审。第一例 native TraceEnd 的SAR字段仍为默认占位值，不可引用；第二例才改为写入原规则检查器计算的SAR。两次源码快照分别保存。
- 两例的SQLite写入角色回填都出现 coverage_checks 行数与动作数不一致警告。未擅自修改官方回填算法，也不把SQL检查分数当作无误的独立危害真值。运行日志中的角色与动作身份不依赖这个回填。
- 生命周期记录仅覆盖实际进入工具处理函数的调用；被SDK过滤、未进入处理函数的提案不在该文件中，应另看原始模型响应。处理函数返回也不代表操作成功或外部影响已经实现。
- 原生 trace 仍是事后排序文件，因此上一轮投影不会自动升级为在线预警数据。增强生命周期和到达记录需要单独的模型接入协议。

## 5. 真实数据已经指出的下一步模型缺口

两例共47个真实生成的工具调用，**没有任何一个工具名属于旧原型硬编码的 `payments.write / filesystem.write / shell.exec`**。把它们直接丢进旧模型，会错过实际的付款授权、申请提交、对外消息和敏感资料读取。这不该通过随意改名掩盖，而应建设有来源的工具能力/副作用映射。

优先升级次序因此明确：

1. 根据公开工具定义和实际角色职责生成工具/角色语义，再由知识模板选择状态结构；隐藏评分规则不进入抽取器。
2. 允许只观察到部分动作范围时表达“未知”，把可用证据层级与需要完整绑定的授权修正能力分开；不能为了通过v3校验伪造principal/资源。
3. 原生生命周期接入后研究动作前风险与动作后证据更新，并补任务级完整对照数据。被预算截断的任务保留为截断记录，不当作安全样本。
4. 再检验长轨迹的推断规模与真正MAS对照方法；当前12个二值变量的精确推断不能直接承诺覆盖实际多动作任务。

本轮尚未解决自动知识子图、完整数据集、固定DAG实验协议、可扩展推断或baseline优势。它使这些后续设计开始有真实运行证据，而不是只依据合成轨迹。

```powershell

```
