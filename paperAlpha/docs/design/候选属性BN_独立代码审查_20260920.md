# 候选属性 BN：独立代码审查

## 审查范围

先核对 `paperAlpha/README.md` 项目宪章，再只读检查：

- `src/paperalpha_monitor/choice_attribute_bn.py`
- `src/paperalpha_runtime/purchase_attribute_adapter.py`
- `configs/catalogue_choice_attributes_v1.json`
- `tests/test_choice_attribute_bn.py`

为判断继承语义，另只读追踪 `exclusive_dispatch_bn.py`、`exclusive_purchase.py`、`workflow_risk_bn.py` 和现有采集顺序。未修改被审代码，未调用 API、未训练、未提交 Git；因目标测试文件包含 `fit`，本轮未以运行测试作为审查证据。仅做了四类无训练的局部复算：保修字符串、非法分组世界质量、特征矩阵秩，以及共享授权路径/风险梯度。

## 明确发现

### 1. 高：适配器没有证明目录和规划文本已实际对买方可见

`purchase_attribute_adapter.py:13-17` 直接从准备态 `prefix["branches"]` 复制目录，并自行填写 `record_id`、`sequence=prefix["cutoff"]`、`source="pre-buyer-assignment"` 和 `visible_to=actor`。它没有读取或核对实际 buyer request、收件人、传输序号或请求正文。

这不是单纯缺少真实性证明：现有采集器在 `collect_exclusive_purchase.py:96-100` 先保存 forecast prefix，之后才发 buyer 请求。因此在该截止点，目录和 planner 回复是编排器准备发送的输入，不是已经送达买方的观测。`choice_attribute_bn.py:95-100` 只检查这些自报字段的形状；记录哈希只能证明对象之后没变，不能证明发生过传递。这与配置 `catalogue_choice_attributes_v1.json:11` 要求运行适配器独立验证实际可见性的边界不一致。

当前属性与候选动作的**内部绑定**是严格的：`choice_attribute_bn.py:114-124` 会核对 actor、SKU、金额、币种、资源、节点、单次限额和 planner 文本。但准确表述只能是“绑定到准备态 buyer 输入”。若要称“买方实际可见”，应以真实 buyer request/journal 的记录 ID、接收方、正文摘要和序号为证；或者明确将预测条件写成“已知且保证随后投递的输入”。

### 2. 高：属性输入没有保证一份买方目录只对应一个互斥组

继承层 `exclusive_dispatch_bn.py:52-53` 只保证每个动作恰属一个组，`32-43` 只保证每个组内部属于同一 actor/node；它允许同一 actor 的同一目录被拆成多个组。`AttributedDispatchInput._check_attributes` 又只按 actor 检查整份目录覆盖，没有检查该 actor 的全部目录候选是否落在同一 `choice_group`。

局部复算将 buyer-a 的 basic/enhanced 拆成两个单候选组后，构造器接受输入；零参数下“两件同时派发”的总概率为 `0.25`。正常 `compile_input` 当前确实为每名买方生成一个组，所以现有适配路径不触发，但公共输入契约仍不能保证“该买方对这一有限目录最多选一个”。

若一名 actor 将来允许多个独立采购槽位，属性证据也应按 `choice_group/slot` 键控，而不是只按 actor；否则应显式拒绝同一 actor 的多组划分。

### 3. 高：保修正则会把否定、条件和可选购文本当成确定正属性

`choice_attribute_bn.py:29-42` 只统计 `<number>-year warranty` 的字面命中次数。恰好一次即返回 `status="literal_claim_only"` 和确定年数，没有检查否定、条件、范围或另购语境。局部复算结果如下：

- `No three-year warranty is included.` → `years=3.0`
- `A three-year warranty may apply.` → `years=3.0`
- `Three-year warranty if registered.` → `years=3.0`

这些值随后在 `142-144` 行进入 `claimed_warranty`，且 `warranty_unknown=0`。现有测试 `test_choice_attribute_bn.py:43-47` 只覆盖正常字面、无数字和多个匹配，没有覆盖上述歧义。

若字段含义是“随商品声称提供的保修”，上述情况必须保守标为 unknown；更稳妥的是使用实际买方目录中的结构化 `warranty_years/status`。若坚持仅做字面模式，则字段不能解释为确定保修属性。

### 4. 中：模型名称是 choice，但随机变量仍是实际 `tool_dispatch`

`AttributeChoiceWorkflowRiskBN` 继承 `ExclusiveDispatchWorkflowRiskBN`；`exclusive_dispatch_bn.py:28-29` 强制所有事件语义为 `tool_dispatch`，互斥证据也是 `at_most_one_dispatch_in_window`。因此 softmax 类别实际是“本窗口无派发或某候选被派发”，不是独立的 buyer choice 或 proposal 节点。

当前应用协议在合法 buyer 回复解析后立即执行一次本地模拟派发，所以完整成功流程中三者可以确定映射；但解析失败、请求失败或未来加入审批/取消后不再等价。论文和接口不能直接把这里的概率写成“选择概率”或“提案概率”，除非同时声明并验证该确定映射。

### 5. 中：当前目录不能识别大多数单独属性系数

按 `attribute_rows` 对仓库固定两买方目录穷举 economy/balanced/quality，候选矩阵为 `12×10`、秩 `9`；组内“enhanced-basic”差分矩阵为 `6×10`、秩仅 `3`。差分中恒为零的列包括：

- `dispatch_bias`
- `priority_economy`
- `priority_quality`
- `warranty_unknown`

每组价差恒为 `30/90`，保修差恒为 `2/3`，所以成本、保修及其优先级交互只能识别少数组合方向，不能分别解释。无放弃标签时，共同 bias 和 priority 主效应只能推动“派发相对不派发”，并出现完全或准完全分离；L2 和参数边界可给出唯一数值，但不构成数据识别。

`test_choice_attribute_bn.py:131-144` 用三个样本验证梯度、优化和恢复，却没有放弃、授权事实或风险监督，也没有报告设计/Fisher/Hessian 秩。仅 dispatch 标签时三个授权先验没有数据梯度；仅系统风险标签时选择率与授权失败率又可相互补偿。后续必须按参数块报告有效标签数、差分设计秩和分离情况，不能解释单个属性或授权系数。

### 6. 中：尚无同特征、同标签的独立 softmax 对照

`choice_attribute_bn.py:174-177` 精确实现标准 outside-option conditional logit：

`p_j = exp(x_jθ) / (1 + Σ exp(x_kθ))`，`p_none = 1 / (1 + Σ exp(x_kθ))`。

因此相同属性、标签、权重、正则和下游策略编译器的独立 softmax 应逐点等价，并继承 IIA。配置 `catalogue_choice_attributes_v1.json:13` 也明确要求 same-feature/same-label control；但当前 `test_choice_attribute_bn.py:147-152` 只比较不含这十项属性的旧模型，这是特征消融，不是等信息对照。仓库当前没有第二套使用 `attribute_rows` 的独立 conditional-softmax 实现。

所以本组件现在只能称为“标准属性 conditional logit 接入既有策略 BN”，不能把选择层表现归因于 BN。

### 7. 低：可执行图数值正确，但单独交付时属性来源身份不完整

组内互斥公式本身正确：`choice_attribute_bn.py:174-177` 使用 `[0,u1,…,uk]` softmax；`exclusive_dispatch_bn.py:89-99` 将组内多选世界置为 `-inf`。`103-114` 的顺序二值 CPT 使用剩余类别条件概率，连乘后恢复原 categorical 分布。

但属性模型未覆盖 `probability_graph`。继承导出只带 `input_sha256` 和策略 registry 身份，不带 `model`、`attribute_program_sha256`、feature names 或参数快照身份；这些只在 `predict/parameters` 中返回。图可执行，却不能靠图本身判断由哪一版冻结属性程序生成。顺序 CPT 中“前一候选 → 后一候选”的边只是 categorical 分解顺序，不是时间、因果或学习到的候选影响，解释层需明确标注。

另外 `choice_attribute_bn.py:161-164` 只验证配置的 feature 列表和保修缩放，没有验证 `schema`、reference 与证据边界字段；配置元数据即使与实现矛盾，只要这两项不变仍会被接受。

## 已确认正确的部分

1. **无直接全局策略或未来标签特征。** `attribute_rows` 只读取 planner priority、该 actor 的目录价格/描述和可见单次限额；`choice_attribute_bn.py:172` 为三个授权参数列补零。全局合同和授权事实只进入下游风险图，不进入 softmax score。严格字段也会拒绝把 `chosen_sku` 直接塞入属性证据。
2. **合法单组内的互斥和 none 质量正确。** 对当前两组、每组两个候选的夹具，只有 `3×3=9` 个有限质量世界；同组双选条件为零概率。
3. **共享授权组合和梯度代数正确。** 选择 score 的授权列为零；`workflow_risk_bn.py` 将 AuthorityProofGraph score 放入最后三个 prior 索引，再与选择质量相加。风险梯度和条件梯度分别使用联合 score 期望，公式正确；共享根事实会在多个动作的 `failed:*` 路径中复用，但不会反向改变选择概率。
4. **现有测试提供的是数值自洽证据，不是语义识别证据。** `test_choice_attribute_bn.py:56-65` 比较预测与标量图并做有限差分，能发现数值实现错误；它没有证明实际可见性、参数可识别、共同上游选择依赖或 BN 独占优势。

## 审查结论

当前代码已正确实现“给定一个可信选择组时的属性 softmax＋共享授权/预算风险组合”，也没有把全局预算或未来选择标签直接放进 choice score。但在宣称候选属性已被 API 证据绑定或具有可解释学习结果之前，至少需要修复：真实 buyer request 可见性锚定、actor/slot 与目录的一一绑定、歧义保修处理，并补齐参数秩诊断和同信息 softmax 对照。
