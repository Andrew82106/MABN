# 初始任务与职责证据：接入现有v7，不增加风险层

## 实质进展

上一轮四类真实采集发现90个动作的职责类别全部unknown。本轮从各运行**实际第一条API请求**提取原始任务及协调者可见的职责描述，使用4次gpt-5.5调用分类17个角色条目，并将这些分类接入现有v7角色条件概率表。215条观测全部完成回放，90个动作选用了不同于unknown的角色表项。

没有新建模型版本或增加参数，仍为345参数。没有训练，没有新准确率，也没有补造可信授权、全局预算或工作流DAG。

## 1. 初始任务不是运行中的Agent主张

新增`paperalpha_runtime/initial_task_context.py`，明确区分三类东西：

- **原始任务**：首个API请求中真实的user输入。
- **声明的职责**：同一请求的hub系统指令中，协调者自身职责及列给协调者的各专员描述。
- **实际动作**：原统一运行日志中的工具入口、消息和返回。

输入适配器只识别已核读的HarnessAudit hub提示格式，检查输入任务和系统提示中的任务一致、角色清单与run_started一致；不读任务YAML、工具必要性/禁止清单、事后规则标签或后续请求。不是任意MAS提示格式的通用解析器。

所有文本保留原文、来源字段、哈希和引用位置。职责描述确实供协调者使用，不代表每个专员都看过同一份全局任务，也不等于专员的完整有效系统提示。

初始内容本来在运行之前存在，但**本轮职责分类是在运行结束后离线完成**。回放只能检验这些初始可观测材料是否能接入，不能报告实际在线预警延迟或提前量。

## 2. 职责分类怎样参与BN

分类只使用原始任务及职责描述，输出已有五类中的一类：unknown、reader、reasoner、reviewer、executor。每个条目必须引用该角色自身描述里的原文；不确定时映射unknown，不输出授权、风险分数或图结构。

实际4次API请求：输入5,191 tokens、输出657 tokens；4份结果都通过字段、角色身份与引用检查。17个角色条目为8个reasoner、8个executor、1个reviewer。

引用检查不等于语义真值。例如“确认供应商侧的安排”可以有审核或外部联系的混合职责；现有粗分类会损失细节，分类器也可能过度自信。本轮保留原输出，不把17个有引用条目声称为17个正确分类，没有人工标注准确率。

新增`ContextualKnowledgeCompiler`：

1. 从真实首请求重新构造初始上下文，再核验分类引用；
2. 显式选择`role_mode=predicted`才将预测职责映射到已有条件表；默认unknown可作为同输入对照；
3. 若显式工作流把不同职责的Agent归到同一节点，合并类别设为unknown并记录冲突，不强行挑一个；
4. 后续日志按原到达顺序进入v7，职责选择影响实际概率计算，不只是解释文字；
5. 保存分类出处和未验证语义，禁止与另一份外部角色配置静默覆盖。

BN参数和训练方程不变，现有解析梯度仍可训练被选中的表项。API分类器和离散类别选择本身不在梯度里。当前这仍是共享结构＋角色条件表，**不是每个职责已经生成了完整专属子BN**。

## 3. 资源引用接到了哪里，没接到哪里

从初始任务保留`DL-CUST-*`客户引用、`DL-*`请求引用的原文位置；动作侧只在实际API公开参数schema声明了Customer ID/Request ID的对应字段时，读取该字段。不同类型不互相混用。

比较结果只有“在原任务中出现”“未出现”“未知”。这不是允许/禁止判定：

> “不要访问DL-CUST-019”也提到了DL-CUST-019，因此出现过绝不能当成得到授权。

真实四条轨迹共96条此类引用，全部在原任务中出现。但原生检查器仍有资源规则命中，说明**客户/请求ID一致远不等于具体对象选对**：保单、方案、供应商线程、批准与参数约束还需要更细的来源关系。

本轮引用比较只放入解释侧观察，**尚不进入BN分数**，也不填补原本缺失的authenticated principal/resource。没有把客户号当执行主体，或把request_id当全部资源绑定。90个动作的权限仍unknown，绑定与原v7完全相同。

四个任务的采集状态与标签保持不变，尤其预算截断任务依然不能作为完整任务训练样本。角色输入接通没有产生新的负样本、独立验证集或MAS原方法结果。

提取器冻结源码在提取时保存。随后给同一模块新增资源引用函数，但不修改冻结副本；回放重新生成实际请求、分类和引用，逐项与API原始响应核对。不能把后加函数当成分类请求时已经存在的实现。
