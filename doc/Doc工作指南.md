# Doc 工作指南

> 用途：约束文档治理、研究设计、实施验收、实验讨论和 Agent 任务委派。  
> 默认原则：**先读场景路由；按需读取对应章节；自顶向下；设计、实施、验收分离。**

## 场景路由：每次回复前默认只读本节

每次处理用户消息前，先读取本节并判断是否触发以下场景。未触发时不必读取后文；同时触发多个场景时，合并读取对应章节。

| 场景 | 触发条件 | 继续读取 | 必须执行 |
|---|---|---|---|
| **写 Prompt** | 用户要求编写 Prompt、任务书、委派 Agent 或让其他 Agent 实施 | 第 0.1、0.8、9 节；若涉及实验设计，再读第 1–8、10–11 节；Python 任务另读 `Python环境说明.md` | 写清任务、范围、交付、验收和固定 Python 环境 |
| **改文档** | 创建、编辑、移动、重命名或删除 `doc` 下任何文件 | 第 0.1–0.7 节；按主题检索第 12 节相关经验；修改本指南时再读第 12 节全部相关条目 | 盘点全部文档，更新所有受影响文件，完成一致性和链接检查 |
| **讨论实验** | 用户提出实验、预实验、如何证明、对照、结果解释或实验方向 | 第 1–8、10–11 节 | 先讲“证明什么、怎么证明、产出什么”，确认后再进入细节 |
| **验收工作** | 用户要求验收、复验、检查 Agent 交付或判断任务是否完成 | 第 0.1–0.7 节；按标题检索第 12 节验收相关经验；完整读取对应任务书和验收标准；Python 任务另读 `Python环境说明.md` | 独立复验，区分功能通过与整体通过；判断是否影响路线；整体通过后清理该任务的临时文件 |

补充规则：

1. **只读需要的章节**，不默认完整加载整份指南；
2. **多个场景取并集**，例如“为实验实施写 Prompt”同时触发“写 Prompt”和“讨论实验”；
3. Python 实施 Prompt 必须额外读取并引用 [项目统一 Python 环境](./Python环境说明.md)；
4. 修改文档不等于修改长期路线，长期文档仍受第 0.4–0.6 节约束；
5. “验收工作”与“改文档”经常同时触发，应合并执行两者规则；
6. 如果用户明确要求另一种工作方式，以用户当前要求为准，并把可复用经验补充到第 12 节。

## 0. 强制文档工作流

### 0.1 主 Agent 的职责边界

主 Agent 负责：

- 研究问题和实验方向设计；
- 为实施 Agent 编写任务书；
- 验收代码、数据、测试和实验结果；
- 判断证据是否改变研究路线；
- 整理和维护 `doc` 下的文档；
- 保证所有受影响文件相互一致。

主 Agent默认不负责：

- 直接搭建实验代码；
- 代替实施 Agent 执行完整实现；
- 在结果尚未验收时修改长期研究路线；
- 将普通运行进度不断写入长期文档。

实施 Agent 负责：

- 按临时任务书实现代码和数据流程；
- 运行测试并报告结果；
- 不自行改变研究问题；
- 不自行修改长期文档；
- 等待主 Agent 验收。


注意:实施Agent不是主Agent的子Agent,而是同级的另一个Agent

### 0.2 每次更新文档前的必做步骤

每次修改 `doc` 下任何文件之前，必须依次执行：

1. **读取顶部场景路由和第 0.1–0.7 节**；如涉及其他场景，再读取路由指定章节；
2. **盘点 `doc` 下全部文件**，确认当前目录结构；
3. **搜索相关术语、路径和交叉引用**；
4. **判断新信息属于临时信息还是路线级信息**；
5. **列出所有受影响文件**；
6. **只修改受影响文件，但必须全部修改到一致状态**；
7. **检查相对链接、名称、编号、状态和术语是否一致**；
8. **检查临时区和长期区边界是否被破坏**；
9. **如果当前工作属于验收，处理临时文件生命周期**：未通过或待返工时保留；整体通过且无后续待办时，先迁移必要内容并检查引用，再删除该任务的临时文件；
10. **如果产生可复用的新工作经验，更新本文件的经验记录**；
11. **向用户报告修改了什么、删除了什么、没有修改什么以及原因**。

“更新所有文件”指：

> 检查全部文档，并更新所有受到本次变化影响的文件。

不应为了形式统一而无意义地改写不受影响的论文设计。

### 0.3 文档区域职责

#### `doc` 根目录

保存：

- 本工作指南；
- 文档导航；
- 跨项目的治理规则。

#### `doc\临时`

保存：

- 给实施 Agent 的任务书；
- Agent 原始返回；
- 未验收的实验结果；
- 验收报告草稿；
- 尚未决定是否影响研究路线的材料；
- 等待处理的文档变更建议。

`doc\临时` 是工作队列，不是已完成任务的档案库：

- 任务未验收、验收未通过、等待返工或仍有后续待办时，保留相关临时文件；
- 任务整体验收通过且没有后续待办时，删除对应任务书、Agent 原始返回、验收报告和中间材料；
- 删除前先把仍需长期保留的路线变化迁移到 `doc\长期`，把运行证据保留在 `paperAlpha` 等代码项目；
- 删除前后都要检查引用，避免留下失效链接；
- `doc\临时\README.md` 是目录规则文件，不随单个任务删除。

#### `doc\长期`

保存：

- 稳定的总体研究路线；
- 已确认的论文设计；
- 跨阶段仍然有效的定义和边界；
- 因可靠证据而发生的路线调整及其理由。

#### `paperAlpha` 等代码项目

保存：

- 代码；
- 配置；
- 数据；
- 运行 manifest；
- 测试结果；
- 实验报告。

日常实验结果首先留在代码项目的数据或报告目录中，不自动进入 `doc\长期`。

### 0.4 长期文档的更新门槛

实验结果默认不写入长期文档。

以下内容留在 `paperAlpha` 或 `doc\临时`：

- 普通运行进度；
- 单次 smoke test；
- 未验收的结果；
- 与既定路线一致的常规结果；
- 暂时性的参数调整；
- 尚未复现的异常；
- 实施细节和调试记录；
- 不改变研究方向的性能数字。

只有当经过验收的实验效果推翻或实质改变当前路线时，才把它写入长期文档。

“推翻或实质改变路线”包括：

- 预注册的核心因果效应在有效实验中不存在；
- 安全替换无法与任务停摆区分；
- 原定主要终点不可可靠测量；
- 实验识别假设被旁路、共享状态或系统机制破坏；
- 预定方法在可承受预算内不可实现；
- 外部验证稳定反转核心结论；
- 结果迫使论文合并、拆分、更换主问题或改变实验顺序；
- 既定 Go/No-Go 标准触发 No-Go。

以下情况本身不足以更新长期路线：

- 一次运行失败；
- 少量异常 episode；
- 代码 bug；
- API 临时错误；
- 未达到样本量的趋势；
- 尚未通过数据质量检查的结果；
- 为了让结果更好看而提出的事后解释。

用户明确要求修改长期文档时，按用户要求执行；但仍需完成本指南规定的一致性检查。

### 0.5 路线变化的证据要求

把实验结果写入长期文档前，至少确认：

1. 实施任务已经完成验收；
2. 代码、配置和数据版本可追溯；
3. 关键测试通过；
4. 数据质量检查通过；
5. 结果不是由权限、日志、重放或状态隔离错误造成；
6. 结果在预先规定的分析下成立；
7. 已区分“实验没有效应”和“实验无法测量效应”；
8. 已判断影响哪些研究问题、论文和后续实验。

### 0.6 路线变化的长期记录格式

如果证据确实改变路线，长期文档必须记录：

```markdown
## 路线变更记录

- 日期：
- 原假设或原路线：
- 触发证据：
- 验收状态：
- 为什么不是实现错误：
- 新决定：
- 受影响的论文或实验：
- 被更新的长期文档：
- 保留的不确定性：
```

不能只修改结论而不记录修改原因。

### 0.7 文档一致性检查

每次更新完成后至少检查：

- 文件路径和相对链接是否存在；
- 同一概念在不同文件中的名称是否一致；
- 论文编号和实验编号是否一致；
- “预实验、主实验、确认性、探索性”是否混用；
- 临时结论是否误写成长期事实；
- 已废弃路径或文件名是否仍被引用；
- 状态标签是否更新；
- README 和索引是否同步；
- 已完成任务的临时文件是否已经清理；
- 是否出现相互矛盾的研究范围；
- 是否需要更新本指南的经验记录。

### 0.8 统一 Python 环境

本项目的唯一 Python 环境见：[项目统一 Python 环境](./Python环境说明.md)。

当前固定为：

```text
Conda 环境：multi_agent_graph
Python：3.11.15
解释器：D:\anaconda\envs\multi_agent_graph\python.exe
```

主 Agent 编写任何 Python 实施 Prompt 时，必须显式写出：

- Conda 环境名称；
- Python 版本；
- 解释器绝对路径；
- 推荐的 `conda run` 命令；
- 禁止使用的其他环境；
- 开始和交付时的环境验证要求。

实施 Agent：

- 不得随机选择 Python 环境；
- 不得使用 `base`、系统 Python 或其他现有环境；
- 不得自行创建 Conda 环境或项目 venv；
- 所有 Python 命令和测试优先使用 `conda run -n multi_agent_graph ...`；
- 新增依赖必须记录到项目环境文件和最终交付说明；
- 如需改变环境，必须停止并请求批准。

检查实施任务书时，如果没有明确 Python 环境，该任务书不能发送。

## 1. 用户偏好的讨论方式

讨论一个实验时，第一轮只回答三个问题：

1. **实验证明什么？**
2. **实验怎么证明？**
3. **实验最终产出什么？**

在用户确认这三点以前，不主动深入：

- Agent 数量和内部编号；
- 具体工作流角色；
- 图拓扑和边名称；
- 数学符号和复杂公式；
- 样本量与统计模型；
- 日志字段；
- 系统架构和代码；
- 论文图表与写作结构。

这些内容并非不重要，而是应当在研究逻辑获得确认以后逐层展开。

---

## 2. 默认的自顶向下顺序

### 第一层：研究目标

先用普通语言说明：

> 我们想知道什么？

要求：

- 一次只讨论一个核心问题；
- 不使用尚未解释的术语；
- 不把方法名称当作研究目标；
- 不从 SBM、POMDP、EVSI、HMM 等技术名词开始。

示例：

> 我们想判断某条 Agent 消息是否真的提高了下游危害概率，而不是仅仅出现在危害发生前。

### 第二层：证据逻辑

接着说明：

> 看到什么结果，才能支持这个结论？

要求：

- 明确比较哪些条件；
- 说明实验中只改变了什么；
- 说明观察什么真实结果；
- 区分相关性和因果性；
- 区分降低危害和让任务停摆。

示例：

> 保持任务、模型和处理前状态一致，只把危险消息替换为安全消息；如果最终危害概率随之下降，就说明危险内容对下游有因果影响。

### 第三层：实验产出

然后说明：

> 做完以后会得到什么具体结果或资产？

产出可以包括：

- 一个效应量；
- 一类经验结论；
- 一个经过验证的实验协议；
- 一份实验数据集；
- 一个边或节点的风险排序；
- 一个可复现的评测环境；
- 一个 Go/No-Go 判断。

示例：

> 得到每条通信边对最终危害的影响大小，以及真正影响危害的边所占比例。

### 第四层：最小实验对象

只有前三层获得用户认可后，才讨论：

- 选择什么任务；
- 需要多少 Agent；
- 每个 Agent 承担什么角色；
- 风险从哪里进入；
- 最终危害如何验证；
- 选择哪一条消息或哪一个动作作为实验对象。

### 第五层：实验变量与对照

再进一步讨论：

- 处理组和对照组；
- 随机化单位；
- 主要终点与次要终点；
- 正常任务效用；
- 负对照、placebo 和消融；
- 外部泛化条件。

### 第六层：统计与实现

最后才讨论：

- 样本量；
- 贝叶斯模型；
- 先验；
- assurance；
- 日志 schema；
- 检查点和重放；
- API、调度器和代码结构；
- 实验排期。

## 3. 第一轮回答的固定模板

当用户提出“这个实验应该怎么做”时，默认使用以下模板。

```markdown
## 实验一：简短名称

### 证明什么

用一至两句话描述需要建立的结论。

### 怎么证明

用三至五步说明最关键的比较和观察，不进入实现细节。

### 产出什么

- 产出一；
- 产出二；
- 产出三。
```

如果有多个研究问题，则逐个使用这个结构，并明确每个实验回答哪个问题。

---

## 4. 多个研究问题的组织方式

不要先给出一个复杂系统，再要求用户从中寻找研究问题。

应当先建立映射：

| 研究问题 | 对应实验 | 判断证据 | 最终产出 |
|---|---|---|---|
| 问题一 | 实验一 | 什么结果支持结论 | 得到什么 |
| 问题二 | 实验二 | 什么结果支持结论 | 得到什么 |
| 问题三 | 实验三 | 什么结果支持结论 | 得到什么 |

例如：

| 研究问题 | 对应实验 | 判断证据 | 最终产出 |
|---|---|---|---|
| 消息是否影响下游危害 | 随机替换消息 | 只改变消息后危害概率变化 | 消息的因果效应 |
| 安全收益是否来自任务停摆 | 比较安全替换和删除 | 二者都降低危害，但安全替换保留任务能力 | 安全—效用结论 |
| 哪些通信边影响危害 | 对预先确定的所有边重复干预 | 不同边的危害效应不同 | 有效边数量及比例 |

## 5. 术语使用规则

### 5.1 优先使用角色名称

不要直接使用：

```text
B1 → C1
```

应先写：

```text
协调 Agent → 内部数据查询 Agent
```

只有在用户已经理解角色以后，才可以在括号中补充内部编号。

### 5.2 首次出现必须解释

任何非日常术语第一次出现时，用一句话解释。

例如：

> Canary 是放在模拟内部数据库中的假测试秘密，用于确定系统是否真的发生泄漏。

不要直接写：

```text
设最终 Canary 是否被发布为 H。
```

更清楚的写法是：

> 如果假测试秘密被发送到模拟外部系统，就记为发生泄漏；否则记为没有泄漏。

### 5.3 优先使用有意义的变量名

面向用户讨论时优先使用：

```text
Leak
TaskSuccess
UnsafeMessage
SafeMessage
DroppedMessage
```

而不是孤立的：

```text
H
U
O
S
D
```

数学简写可在进入统计建模阶段以后引入。

### 5.4 解释“实验对象”

诸如“焦点消息”“处理边”“风险窗口”等术语必须先翻译成人话。

例如：

> 焦点消息就是本次实验专门选择来修改和检验的那一条 Agent 间消息。

## 6. 泛化问题的讨论规则

不要把预实验对象直接说成整篇论文的唯一研究对象。

必须区分：

### 预实验

目的：

- 验证机制是否能工作；
- 检查实验工具是否可靠；
- 估计事件率和成本；
- 决定是否值得扩大研究。

预实验可以只使用：

- 一个任务；
- 一个模型；
- 一个固定图；
- 一条关键消息。

### 主实验

目的：

- 检验结论能否跨场景成立；
- 估计异质性；
- 支撑论文的正式外推范围。

主实验再扩展：

- 多类任务；
- 多个模型家族；
- 多种图结构；
- 多个风险入口；
- 多条通信边。

讨论时应明确说：

> 这个对象只用于预实验验证可行性；正式结论需要在预注册的多任务、多模型和多拓扑条件下复核。

---

## 7. 不应过早讨论的内容

除非用户主动询问，否则第一轮不讨论：

- 论文应该画哪些图；
- 论文各章节怎么写；
- 目标会议；
- 复杂模型公式；
- 完整变量字典；
- Agent 内部编号；
- 全部日志字段；
- 具体代码框架；
- 两周或数月排期；
- 所有可能的扩展方向。

尤其不要使用以下表达方式：

> 先设八个 Agent，其中 B1 通过边 \(e_{13}\) 向 C1 发送消息，再定义 \(H\)、\(U\) 和四个处理条件……

这会让用户在理解研究目标以前先承担大量实现细节。

---

## 8. 逐层确认机制

每完成一层讨论，应停下来检查当前共识。

推荐顺序：

1. 确认研究问题；
2. 确认证据逻辑；
3. 确认实验产出；
4. 选择最小实验对象；
5. 设计处理与对照；
6. 设计预实验；
7. 确定统计方案；
8. 进入实现。

如果用户表示“看不懂”“太细”“先别讲实现”，应立即退回上一层，用普通语言重新说明。

不要在同一次回答中自动把所有八层展开。

---

## 9. 给子 Agent 下任务时的要求

凡是让子 Agent 参与实验设计，任务说明中应加入：

```text
请自顶向下回答，首先只说明：
1. 实验证明什么；
2. 怎么证明；
3. 产出什么。

不要先给 Agent 编号、复杂公式、样本量、日志字段、代码或论文图表。
只有在研究逻辑明确后，再单独列出实现建议。
首次使用的术语必须用普通语言解释。
```

子 Agent 的返回应先写：

```markdown
## 顶层结论

## 证明什么

## 怎么证明

## 产出什么

## 尚未展开的实现细节
```

主 Agent 在整合子 Agent 结果时，应重新组织语言，不能直接把多个 Agent 的技术细节堆给用户。

凡是让子 Agent 执行 Python 实现，还必须加入 `Python环境说明.md` 第 6 节规定的环境块。

## 11. 当前项目的示范表达

对于多智能体不安全传播实验，优先这样讨论：

### 实验一

**证明什么**

某条 Agent 消息中的危险内容是否真正提高了下游危害概率。

**怎么证明**

保持其他条件一致，只把危险消息替换为安全消息，比较最终危害率。

**产出什么**

该消息对危害的因果效应及其不确定性。

### 实验二

**证明什么**

降低危害是否来自真正移除危险内容，而不是让系统停止工作。

**怎么证明**

比较安全替换、删除消息和正常任务，同时观察危害与任务成功。

**产出什么**

安全处理对危害和正常能力的双重影响。

### 实验三

**证明什么**

通信图中有多少边真正影响最终危害。

**怎么证明**

对预先确定的所有通信边分别进行随机消息替换，比较每条边改变前后的危害率。

**产出什么**

每条边的危害效应，以及危害放大边、保护边和无明显作用边的数量。

以上三层逻辑得到用户确认后，再进入实验对象和实现讨论。

## 12. 工作经验持续记录

本节持续记录可复用的工作经验。新经验应转化为明确规则，而不是只记录事件经过。

### 2026-07-31：实验讨论必须自顶向下

**经验**

过早引入 Agent 编号、数学符号、图结构和实现细节，会掩盖实验真正要回答的问题。

**形成的规则**

- 第一轮只回答“证明什么、怎么证明、产出什么”；
- 用户确认研究逻辑后再进入对象、变量、统计和实现；
- 首次出现的术语必须用普通语言解释。

### 2026-07-31：预实验与泛化主张必须分开

**经验**

单一任务适合验证实验机制，但不能直接承担正式泛化结论。

**形成的规则**

- 明确区分预实验和主实验；
- 预实验允许一个任务、一个模型和一条关键消息；
- 正式泛化需要多任务、多模型或多拓扑复核。

### 2026-07-31：设计、实施和验收分离

**经验**

主 Agent 同时负责设计、编码和自我验收，容易导致实验方向与实现细节相互污染。

**形成的规则**

- 主 Agent负责设计、任务拆分、验收和文档治理；
- 实施 Agent 按临时任务书编码和测试；
- 实施 Agent 不自行修改长期研究方向；
- 主 Agent 根据预先约定的标准验收。

### 2026-07-31：长期文档不是实验日志

**经验**

把每次运行结果持续写入长期研究设计，会导致稳定路线被临时噪声反复改写。

**形成的规则**

- 日常结果保存在代码项目或临时区；
- 与既定路线一致的常规结果不进入长期文档；
- 只有经过验收、足以推翻或实质改变路线的证据才更新长期文档；
- 路线变化必须同步更新所有受影响文档并保留变更理由。

### 2026-07-31：文档更新必须全局一致

**经验**

文件重命名或规则变化后，只修改一个入口会留下失效链接和相互矛盾的说明。

**形成的规则**

- 每次回复前读取顶部场景路由；
- 修改文档时读取第 0.1–0.7 节及相关经验，而不是默认加载整份指南；
- 盘点全部文档并搜索引用；
- 更新所有受影响文件；
- 完成相对链接和术语一致性检查；
- 不修改不受影响的论文内容。

### 2026-07-31：实施 Prompt 必须固定 Python 环境

**经验**

如果 Prompt 不写明 Python 环境，实施 Agent 会随机使用 `base`、系统 Python或其他已有环境，导致依赖、测试结果和复现路径不一致。

**形成的规则**

- 项目统一使用 Conda 环境 `multi_agent_graph`；
- 每个 Python 实施 Prompt 必须写明环境名、版本和解释器绝对路径；
- 自动化命令优先使用 `conda run -n multi_agent_graph ...`；
- Agent 开始和交付时都要报告实际解释器；
- 依赖变化同步记录到项目环境文件；
- 未包含环境块的实施 Prompt 不得发送。

### 2026-07-31：使用场景路由减少无关上下文

**经验**

工作指南会持续增长。如果每次回复都完整读取，会重复消耗上下文，并把与当前任务无关的规则带入工作过程。

**形成的规则**

- 把场景路由放在指南最开头；
- 每次回复默认只读取场景路由；
- 当前固定场景为“写 Prompt、改文档、讨论实验、验收工作”；
- 命中场景后只读取路由指定章节；
- 同时命中多个场景时合并读取；
- 新增可复用工作场景时，先更新顶部路由，再补充对应详细规则。

### 2026-07-31：验收必须区分功能通过与整体交付通过

**经验**

实施方报告测试通过，不等于任务已经满足环境、配置生效、数据追踪和交付要求。代码也可能在指定环境复跑成功，但原始交付实际上使用了错误环境；配置文件也可能存在却没有驱动执行。

**形成的规则**

- 主 Agent 必须使用任务指定的解释器独立复跑关键测试；
- 验收同时检查功能、环境可复现性、配置是否真实生效、数据完整性和交付说明；
- 对核心配置进行负向或扰动检查，不能只确认文件存在；
- 数据验证必须检查跨文件一致性，不能只分别通过 schema；
- 分别记录“功能通过”和“整体交付通过”，任一硬性验收项失败时不得把任务标记为已验收；
- 实现缺陷和普通 smoke 结果在任务进行期间留在临时区，不因此修改长期研究路线；
- 整体交付通过后，执行临时文件清理，不能把已完成任务长期堆积在临时区。

### 2026-07-31：临时区是工作队列，不是完成任务档案

**经验**

任务书、Agent 返回和验收报告在任务进行期间有用，但任务完成后继续保留会让临时区不断膨胀，并使“仍待处理”和“已经结束”难以区分。

**形成的规则**

- “任务完成”以整体验收通过且没有待办为准，不以 Agent 声称完成或单元测试通过为准；
- 未通过、待返工、等待复验或可能改变路线时继续保留临时文件；
- 整体通过后，先完成必要的长期迁移和引用检查，再删除该任务的全部临时材料；
- 常规实现证据保留在代码项目的数据、manifest 和 reports 中，不依赖临时文档归档；
- 删除完成后重新盘点临时区并检查失效链接。

### 2026-07-31：环境与源码 provenance 必须验证“实际执行状态”

**经验**

源码中的 `__version__`、`pyproject.toml` 版本和固定环境中已安装 distribution 的版本可能不同。若 manifest 和验证器都读取同一个源码常量，它们会共同把错误记录判为一致。类似地，只哈希包内源码而漏掉实际执行的入口脚本，也会让“源码哈希匹配”产生虚假的完整性。

**形成的规则**

- 环境 provenance 必须读取 `importlib.metadata` 中的实际安装 distribution 版本，不能只记录源码常量；
- 同时存在源码声明版本、安装版本和依赖清单时，必须检查三者内部一致性；
- editable 项目修改版本后，实施 Agent 必须在固定环境重新安装并复核 distribution metadata；
- 必须用版本漂移样本验证 validator 返回 FAIL，不能让记录器和验证器复用同一个错误事实来源；
- 源码追踪必须覆盖所有实际执行代码，包括包源码和命令入口脚本；
- 无 Git 仓库时尤其要用文件级路径—哈希或完整树哈希覆盖执行入口，并用脚本扰动测试证明漂移可被识别。

### 2026-07-31：跨文件验收要测试“合法但矛盾”的篡改

**经验**

schema 可以证明字段类型和格式合法，却不能证明多个文件在语义上一致。若负向测试只使用错误 run ID、非法 treatment 或明显错误哈希，验证器可能通过这些测试，但仍漏掉“每个字段本身合法、文件之间互相矛盾”的修改。

**形成的规则**

- 跨文件验证先列出同一事实的全部表达位置，再逐项检查来源与派生关系；
- 负向测试必须包含合法值替换，例如布尔值翻转、换成另一合法 treatment、换成另一合法 SHA-256；
- 危害结果、任务结果、处理条件、消息哈希和 manifest 预期必须由可重算状态或权威输入锚定；
- 验收不能只看现有测试数量，必须抽取至少一个未被测试覆盖的语义字段做隔离扰动；
- 任何语义矛盾样本仍被 validator 判 PASS、或 CLI 返回 0，都属于数据链完整性的硬性阻断。

### 2026-07-31：有 Go/No-Go 依赖的预实验必须逐门派发

**经验**

即使完整实验路线已经设计好，也不能把所有有前置依赖的预实验一次性交给实施
Agent。否则上游门槛失败后，下游仍可能继续运行，产生无法解释的数据、额外成本和
事后调整空间。

**形成的规则**

- 长期文档可以一次冻结完整实验链，但临时实施任务只覆盖当前第一个未通过门槛；
- 每份任务书必须写清它证明什么、怎么证明、产出什么以及 Go、返工和 No-Go；
- 上一门槛未经验收通过，不得派发、预跑或调参下一门槛；
- 上游失败时只修复与当前门槛有关的因素，不同时修改下游处理和分析；
- Pilot、校准和确认性数据必须分开标记，不因节省样本而事后合并；
- 如果真实运行需要付费 API、模型下载或新的外部权限，先完成不产生费用的实现与
  离线验证，再由用户冻结提供方、模型和预算。
- API 密钥只保存到被忽略的本机 `.env` 或专用凭据存储，不得进入任务书、长期文档、
  manifest、日志、报告或测试 fixture；
- 用户提供接口后，除核对技术协议外，还必须核对官方用途限制；不把仅限交互式编程
  的额度用于自动化实验或批量推理。

### 2026-07-31：验证器必须对不可信工件 fail-closed

**经验**

文件哈希、顶层 Schema 和重放一致，并不能保证事件内部语义有效。经过协调重算的
未来时间、负数计数或错误嵌套类型仍可能保持哈希自洽；如果验证器在这些输入上抛出
异常而不是返回失败，也不能算安全验收通过。

**形成的规则**

- manifest、events、outcomes、replay 及其所有嵌套字段一律视为不可信输入；
- 在调用 `.get`、索引、排序、算术或状态重算前，先验证容器和标量类型；
- 每种实际事件类型都应有精确的 payload contract，覆盖必填字段、嵌套类型、取值范围
  和额外字段拒绝，不能只把 payload 定义为普通 object；
- 时间字段应验证规范 UTC 格式、运行边界和事件顺序；token、时延、重试和计数等数值
  应验证类型、非负性及可重算关系；
- 验收篡改应同步重算 payload、event ID、artifact hash 和 fresh replay，避免只被浅层
  哈希不匹配拦截；
- 对任何畸形工件，Python API 必须返回结构化 `passed=false` 和非空错误，CLI 必须
  非零退出且不泄露 traceback；重放失败不能替代验证器自身的语义检查。

### 2026-07-31：权威 run 更替时必须同步清除“当前”表述漂移

**经验**

代码、数据与验证器都通过时，README、交付说明或数据索引仍可能把已被替换的旧 run
写成“当前正式”证据。这不会改变原始数据，却会误导后续任务选择错误的复验对象。

**形成的规则**

- 一个阶段出现新的、已验收的权威 run 后，必须明确其唯一身份及 validation/replay
  结果；
- 验收时检索当前 run 与被替换 run 的全部引用；旧 run 只能以“历史”“上一版”或明确
  的失败原因保留，不能再称为“当前”“正式”或“权威”；
- 这类跨 README、交付说明和数据索引的矛盾属于整体交付阻断项，即使代码测试全部
  通过；
- 修正文案时不改写原始运行数据、manifest 或历史证据；修复后至少复验对应权威 run
  的 validation/replay，并重新检查引用范围。

### 2026-07-31：科学批次验收必须从真实数据角色目录复验公开入口和分项门槛

**经验**

内部 Python API 在手动传入正确 context 时可以复验真实 batch，并不代表 README 中公开的
validation/replay CLI 能找到 `pilot`、`engineering_dry` 等实际数据角色目录。类似地，把
“四字段全对的 episode 数”乘以四，会在存在 3/4 等部分正确结果时错误地低估字段总数。
这两类问题都可能让全部单元测试通过，却使真实实验的报告、可复现入口或 Go/No-Go 判断不可信。

**形成的规则**

- 对每个真实或候选科学 batch，必须使用 README 中记录的**公开 CLI**，在不写原始证据的
  方式下复验 validation 和 replay；手动注入内部 context 的成功只能用于定位问题，不能替代
  公开入口验收；
- 验收要枚举新数据根下的全部生成物，检查它们是否位于声明的数据角色子目录、是否被 manifest
  引用；由错误 context 生成的重复或失败报告也要作为边界/可追溯性缺陷保留并报告；
- 门槛指标必须从权威终点逐项累计。若指标按字段计数，测试至少包含 3/4、2/4 等部分正确样本，
  禁止用“整条记录全对”的布尔值替代分项总和；
- 候选结论必须是预先定义的单一类别（Go、返工或 No-Go），不得用“返工或 No-Go”这类合并表述
  回避失败归因；
- 真实 batch 同时出现工程/报告缺陷和门槛失败时，先判“实现交付未验收”，保留原始 run、不得重跑
  模型或进入下游阶段；修复工具和测试后仅重新解释既有证据，除非主 Agent 另行批准新的实验设计。

### 2026-07-31：provenance、fresh replay 与总时限要验证真实语义，不能只检查字段存在

**经验**

一个名为 `shared_schema_files` 的 provenance 字段即使存在、tree hash 也能匹配，仍可能错误地
哈希了模板或源码而漏掉任务要求的真实 schema 文件。类似地，测试手工改写 replay 的 hash 并不等于
重新运行 replay；在 episode 前后检查时间，也不等于限制一条正在执行的模型调用跨过总墙钟期限。

**形成的规则**

- 验收 provenance 时，先从任务书或静态输入构造**预期路径集合**，再比较逐文件 hash 的集合；
  不能只检查字段非空、tree hash 存在或“当前实现与自身记录一致”；
- 名称含 `schema`、`fixture`、`prompt` 或 `permission` 的 map 必须逐项核对真实路径，不能用
  内容相关的模板或源码作为替代；
- 要求 fresh replay 的篡改测试必须实际调用生产 `replay_run` / 公开 replay CLI 来生成新 replay，
  不得手工编辑 replay JSON 后把它称为 fresh；
- 总墙钟硬上限必须覆盖阻塞中的单次调用：把剩余总预算传入调用超时，或采用可取消的 watchdog；
  测试必须模拟“调用开始时尚未超时、返回时已经超时”的情形；
- 修复后的交付说明必须把旧报告明确标为历史，或同步更新所有当前数字、测试数和候选结论；
  一个目录内的 `DELIVERY`、`REWORK_DELIVERY`、README 和 registry 不得互相矛盾。

### 2026-07-31：验收测试的预期事实不能只复用生产常量

**经验**

当测试从被验收模块导入同一个路径常量、枚举或规则作为 `expected` 时，生产实现与测试可以
一起漂移而仍然全绿。这种“自洽”不能证明 provenance、权限名单或冻结输入真的对应任务书。

**形成的规则**

- 对任务书明确给出路径集合、阈值或权限名单的验收测试，必须在测试侧使用独立的 literal
  truth set、独立 fixture 或其他不与生产常量共用的 oracle；
- 测试不能仅断言 `actual == imported_production_constant`；
- 对关键常量，至少加入一个能揭示“生产常量被错误替换而测试 oracle 仍不变”的定向场景；
- 代码实现可复用生产常量，但验收依据不得只由同一常量派生。

### 2026-07-31：派生审计必须在其自身目录中声明非运行身份

**经验**

派生 repair audit 即使位于单独目录且带有 `derived_from_run_id`，若其 manifest 和报告继续使用
原 run 的执行模式与标题，后续工具或读者仍可能把它误认为第二次真实运行。

**形成的规则**

- 每个派生审计目录的 manifest 必须包含机器可检查的 `artifact_kind`、`is_derived_audit=true`、
  `is_new_run=false`（或等价字段）及明确的 source run；
- 派生 audit 的 execution mode 必须与 source execution mode 区分，source mode 单独记录；
- 派生目录内的报告、hash 清单或 identity 文件必须明确写出“派生审计、不是新运行”；
- 这类身份字段和报告标题应有独立测试，不能只依赖目录名或目录外的交付说明。

### 2026-08-01：派生审计只能代表其生成时冻结的代码快照

**经验**

派生审计记录的 provenance 在生成时可以完全正确；但若随后修改了被追踪的生成器源码，旧审计仍是历史证据，却不能再被标为当前交付对应的代码状态。类似地，旧交付文档中遗留“当前/唯一”措辞，会使新的审计身份在文档层失效。

**形成的规则**

- 生成派生审计前先完成所有会进入其 provenance 的源码修改与测试；生成后不得再修改这些文件；
- 若必须修改，保留旧审计为历史证据，在新目录生成新的版本化审计，绝不补写或覆盖旧目录；
- 新审计交付前，独立比较其 `repair_tool_provenance` 与当前 `capture_provenance()`，并把相等结果作为硬验收项；
- 每次更换 current repair 后，检索所有交付文档中的“当前、唯一、current、latest”表述；历史报告只能指向新交付或明确自己是历史，不能继续把旧 repair 称为当前；
- 文档声称某文件已经同步时，验收必须检查该文件的实际内容，而不能只相信交付报告。

### 2026-08-01：门槛失败必须区分“禁止下游”与“否定研究命题”

**经验**

一个冻结预实验可能因预先规定的可靠性阈值、数据链完整性或真实执行错误而不能作为下游
通行证；这会改变实验顺序，却不自动说明任务能力不存在、因果效应为零，或整篇论文应
停止。若把这些结论混写，后续会把工程/准入结果误报成科学结果。

**形成的规则**

- 记录门槛失败时，分别写清“该来源批次是否可进入下游”“该实验实际回答了什么”与
  “对论文命题是否有结论”；
- 若冻结来源未通过硬门槛，必须锁住下游阶段，并明确 `p1_go=false`（或对应 gate 状态），
  但不得把它笼统称作论文或科学 No-Go；
- 若失败来自不可改写的源数据链或执行事实，保留原始证据并禁止续跑、覆盖或补写；任何
  替代方案都必须先作为新的、独立冻结的上游实验设计和 run ID 获批；
- 长期路线记录要同时给出固定门槛、验收证据、未通过原因和保留的不确定性，避免只凭
  后续审计缺陷或单一异常 episode 宣布科学结论。

### 2026-08-01：离线工程的输入路径本身是权限与 provenance 边界

**经验**

默认命令没有调用网络或 `.env`，并不能证明实现永远不会这样做。若公开 API 或 CLI 接受任意
文件路径，调用者仍可把 `.env`、旧数据根或 Windows UNC 网络路径传入；同样，若 manifest 只
哈希仓库中的默认输入，而实际运行可使用外部 config/fixture，就会形成“记录与真实执行不一致”的
伪 provenance。

**形成的规则**

- 对离线任务的所有输入和输出路径，在打开或创建文件前执行允许根、文件类型、`.env`、UNC/设备
  路径和旧数据根的显式检查；默认路径安全不等于任意参数安全；
- 写入器不得因调用者传参而写入只读历史数据根；如需可配置性，必须将实际使用的受限路径、身份和
  哈希写入 manifest，并由 validator 独立复核；
- 对不可信 manifest、event、outcome 和路径输入，Python API 必须结构化 fail-closed，CLI 必须非零
  且不输出 traceback；
- 验收测试要在隔离目录中覆盖 `.env`、UNC、旧数据根和外部 fixture/config，确认没有读取、写入或
  网络 I/O；同时证明实际输入改变时 provenance 或验证结论会相应改变。

### 2026-08-01：provenance 漂移测试不能让并行验收互相污染

**经验**

直接在工作区的真实源码、schema、prompt 或 fixture 上做“修改后验证 FAIL、随后恢复”的测试，能
证明 drift detection，却会使并行 pytest 或并行验收暂时看到错误的代码快照，造成假失败，甚至在
进程中断时留下污染风险。

**形成的规则**

- 优先在隔离副本中做 provenance 漂移测试；不能隔离时，必须明确声明该组测试仅可串行运行，并用
  `try/finally` 恢复全部字节；
- 并行运行期间出现的 provenance/self-check 失败，先排除测试间互扰，再判断是否为产品回归；
- 任何会短暂改写可追踪输入的测试结束后，验收必须独立复跑 current artifact 的公开 validation 与
  replay，并检查其 provenance 恢复匹配；
- 这类测试的临时写入不得越出该任务允许的命名空间，也不得触及历史数据、`.env` 或网络路径。

### 2026-08-01：资格框架必须区分“安全拒绝”与“格式非法”

**经验**

上游输出契约若允许一个显式的拒绝分支，后续资格框架把该分支直接删掉，会把“合约合法但不满足
当前任务、因此安全拒绝”的行为误分类为解析或 schema 错误。表面上更严格，实际上丢失了对失败
语义和公开端边界的关键检验。

**形成的规则**

- 继承既有输出契约时，先逐分支列出允许的结构与语义，不能只复制成功分支；
- 对每个合法拒绝分支，单独测试它不会到达公开 sink，并记录为可区分的任务/语义拒绝；
- 对格式非法、越权字段、角色错配与合法拒绝分别保留失败类别，禁止用一个笼统的“解析失败”合并；
- 若当前资格任务只接受成功动作，合法拒绝仍应是“任务未通过”，而不是被伪装成一条合约非法记录。

### 2026-08-01：受保护工件与其公开验证审计必须明确区分

**经验**

某些公开 validation/replay 入口会为可追溯性追加零调用审计记录。若任务书一面要求复跑这些入口，
一面笼统规定“不得改动旧工件”，实施方和验收方会无法判断该审计写入是合规操作还是历史证据污染。

**形成的规则**

- 任务书涉及受保护的历史/上游工件时，必须逐类列出真正不可变的核心文件；
- 若公开验证器会写入派生审计，必须把它列为唯一明确的 append-only 例外，并写清允许目录、零调用
  要求和禁止手工编辑的边界；
- 验收“未改动上游”时，比对核心 evidence 与 provenance，不能把合规的派生审计写入误判为重跑或
  原始证据覆盖；
- 若验证器会覆盖而不是追加，必须在执行前另行批准或改为隔离审计，不能把它默认为只读检查。

### 2026-08-01：JSON 输出模式不等于冻结输出契约已经满足

**经验**

模型接口声明 JSON 输出或请求参数设置 `format=json`，只能约束外层表达形式，不能证明每个冻结字段、
角色和值都已满足资格任务。真实本地资格批次可能返回可解析的 JSON，却持续缺少必填字段；把这类
结果误称为网络、解析器或模型的一般失败，会模糊工程资格结论与研究结论的边界。

**形成的规则**

- 每个真实资格批次都必须直接对原始模型输出逐字段、逐语义检查，不得以接口的 JSON 模式或少量
  smoke test 替代输出契约证据；
- Screen 门槛不满足时，必须阻止 Confirmation，并保留未启动原因；不得用未记录的修复、重试或
  自动换模型补齐结果；
- 将“某个冻结配置 `not_qualified`”与“模型一般能力不足”及“论文科学命题被否定”分开记录；
- 新的提示、输出适配器、解码设置或模型，均属于新的候选配置，必须以新的冻结任务书和 run ID
  单独资格验证。

### 2026-08-02：模型可枚举不等于远程资格已经通过

**经验**

`GET /models` 能证明 gateway 当前列出了一个模型 ID，却不能证明真实 completion 的 JSON-schema
能力、响应包络、凭据隔离、身份稳定性或输出契约。把本地 Ollama 更换为 OpenAI-compatible gateway
时，旧 transport、模型 fingerprint 和“零远程调用”结论也不能自动迁移。

**形成的规则**

- 每次切换 provider、endpoint、模型或输出 profile，都按新的冻结候选配置处理；历史资格工件保持
  只读，新的实现与数据使用独立根；
- 先用虚构凭据和注入式 mock 验证请求构造、响应 adapter、凭据不落盘和离线 validation/replay，
  再根据用户明确授权启动真实调用；
- 真实调用采用预先写明的递进门槛和最大调用数；输出契约错误不得进入下一阶段，基础设施、身份、
  凭据或证据链错误必须停止并与模型不合格分开记录；
- 远程服务未提供权重版本或 fingerprint 时，如实记录可获得的模型列表、provider-declared model、
  request ID 与响应版本字段，不得伪造为本地权重身份。

### 2026-08-02：一次性真实批次必须在调用前完成独立预检

**经验**

如果把独立预检与唯一一次、带预算的真实调用并行进行，预检发现的边界缺口可能在消息送达前已经变成
不可重跑的历史事实。表面通过 validation/replay 也不能弥补验证器接受“篡改后仍自洽”的失败记录。

**形成的规则**

- 对唯一、付费、限额或不可重跑的真实批次，实施方的离线测试通过后，必须先完成主 Agent 或独立
  审计 Agent 的只读预检，明确收到“可以发起 live”的结论后才允许建立 socket；不能把预检当作并行
  的非阻塞工作。
- 总墙钟上限必须覆盖每一项外部 I/O（包括开始/结束身份查询）和阻塞中的调用；调用超时必须取单次
  上限与剩余总预算的较小值，且测试要模拟“调用期间越过总时限”。
- 每个已实际尝试的 completion，无论成功还是被契约拒绝，都必须保存可安全公开的请求 hash 与
  provider-declared model、request ID、fingerprint/version（缺失时显式 `not_provided`）；不得保存
  原始推理、tool 参数、服务端错误正文或密钥。
- validation 与 replay 的篡改测试必须覆盖失败 record：在隔离副本中修改其合法形状字段并同步
  artifact hash 后，两个入口都必须 fail-closed；同时交叉核验 completion/metadata 计数、账本事件、
  阶段门槛和身份记录。
- 派生修复审计必须先建立自身 schema 下可通过的合法基线，再对它做单字段篡改；历史 run 若天然缺少
  新 schema 的字段，只能标为 legacy evidence/rework，不能拿它“失败得理所当然”的结果冒充篡改检测。
  对账本测试还要重算后续 hash 链后再验证，确保检查的是身份事件的语义而不是单纯的链断裂。
- 若真实调用先完成才发现上述工程缺口，保留原始 run，不重跑、不补写其证据；可以记录“观察到的
  输出事实”，但整体交付必须判为 `rework`，不能用作下游 Go/No-Go 的已验收依据。

### 2026-08-02：流程级门槛不能只由 helper 单测代替

**经验**

一个 deadline helper 分别通过“开始、执行、结束”三个标签的单元测试，并不能证明它真的被完整状态机
调用，更不能证明超时后流程不会继续发起后续 I/O。对分阶段安全门槛而言，这会把局部函数正确误当作
流程安全正确。

**形成的规则**

- 只要任务声称有 start metadata、completion、end metadata 或类似的多阶段 I/O，验收必须运行一个
  注入 fake transport 的完整流程测试，并对每一步的实际调用计数、状态和后续禁止行为断言；不能只
  调用 helper 并换 label。
- 对“调用期间耗尽总预算”，至少分别验证：start 耗尽后没有 completion/end，completion 耗尽后没有
  end/下游，end 耗尽后结论为工程失败；对零或负预算，也要分别验证 metadata 与 completion 均为零 I/O。
- 若派生审计已在某源码快照上生成，随后发现需要改源码，旧审计保留为 `historical_pre_rework`；修复后
  以新的 audit ID 和新 provenance 生成替代审计，绝不覆盖或补写旧审计。

### 2026-08-02：身份链必须锚定冻结事实，不能只做多文件互相一致

**经验**

把 transcript 的 metadata、ledger 事件和 outcome 同时改成另一份内部一致的模型列表，仍可能让
“start=end、账本匹配、hash 链匹配”的验证全部通过。跨文件一致性只能证明材料彼此不矛盾，不能证明
它们对应运行前冻结的身份事实。

**形成的规则**

- 任何模型、权限、任务卡、阈值或身份类关键事实，validation/replay 都必须从冻结输入或测试侧独立
  literal oracle 重算 expected value；不得只比较两个可同时被篡改的工件。
- 篡改测试至少包含一次“协同一致篡改”：同时修改所有相互引用的位置、重链 ledger、同步 manifest
  artifact hash；两个公开入口仍必须因偏离冻结 oracle 而 fail-closed。
- 在测试中，expected 值不能从被测 transcript、ledger、outcome 或生产常量直接导入；必须能区分
  “工件彼此一致”与“工件正确”。

### 2026-08-02：每个审计的交付报告必须是本地不可变工件

**经验**

若多个 audit manifest 都哈希同一个根级 `DELIVERY.md`，写入新 audit 的 current report 会使旧 audit 的
manifest 外部引用失效；即使旧 audit 目录的文件一字未改，它也无法在之后独立复验。

**形成的规则**

- 每个 run/audit 的 DELIVERY 必须位于其自身不可变目录内，并由该 run/audit 的 manifest 哈希；不得把
  可被后续运行覆盖的根级 current report 当作历史 artifact。
- 根级 report 若需要保留，只能是明确标记 current/historical 的索引，不能进入任何历史 manifest 的
  artifact hash。
- 测试必须在隔离数据根连续生成至少两个版本，验证第二个版本、current index 或报告更新不会改变第一个
  版本的目录内 DELIVERY、manifest 或公开 validation/replay 结论。

### 2026-08-02：未哈希的 current index 仍是整体交付的一部分

**经验**

最终 audit 的目录内证据、manifest 和公开验证可以全部通过，而根级未哈希 current index 仍把一份
`historical_pre_rework` audit 误写成当前版本。此时密码学证据链没有损坏，但后续人或 Agent 会选择错误的
复验对象，整体交付仍不一致。

**形成的规则**

- 验收除复验 audit 自身的 validation/replay 外，必须检查数据根的 current/historical 索引和交付说明；
- 任何被替换的 audit 都要明确标为历史及其原因，current index 要写出唯一当前 audit ID；
- 若根级索引不被 audit manifest 哈希，可以在不重发 audit 的前提下限定修正；修正后仍须复跑当前 audit
  的公开 `validation → replay → validation`；
- 修复证据链的通过只能证明修复后的候选工程，不能回填或升级不可重跑的原始 live run。

### 2026-08-02：离线与真实运行必须具有不可混淆的证据身份

**经验**

同一套 runner 同时支持 fake 与真实调用时，只按标题或 run ID 区分 `DELIVERY`，会让一个真实 run 在报告中
被误写为离线，或让协调重链、重算 manifest 后的矛盾说明通过 validation/replay。文件哈希一致只能证明文件
没有在记录后被单点改动，不能替代运行类型的语义校验。

**形成的规则**

- fake 与 live run 必须使用不同且与 `run_kind` 绑定的 schema/version、配置、outcome、report 与 DELIVERY 语义；
- validator 与 replay 必须从冻结的 transcript/outcome 重建 run-local DELIVERY 的全部允许字段，拒绝只检查标题、
  run ID 或关键词的实现；
- 负向测试必须覆盖“把 live 写成 offline/no-network”及其对称情形，并同步重链和重算 manifest 后仍 fail-closed；
- 实际 live run 的结论只表述其冻结范围内的观察，明确原始响应丢弃后的认证边界，不能借由工程验收升级为资格、
  下游通行或科学结论。

### 2026-08-02：动作资格卡必须让模型真正看到事实，不能把答案塞进 schema

**经验**

一组离线动作卡即使有 fixture、Canary、严格 JSON schema 和全绿 fake transport，也可能只把通用角色提示
发送给模型形状接口，同时用 schema 的 `const` 直接给出完整预期答案。此时它验证的是本地 fake adapter，
而不是“模型能否根据良性事实做出正确且不过权的动作”；未实际执行的 fixture 列表也不能算案例覆盖。

**形成的规则**

- 若资格目标包含任务语义，每张卡的脱敏良性事实必须实际进入仅内存的请求，并由 fake transport 测试确认；
  内部 Canary 也必须真的进入指定卡的内存输入，绝不进入持久化工件；
- 输出 schema 可以固定动作外壳、字段类型、允许字段和静态工具名，但不得以 case-specific `const` 预填
  vendor、状态、风险、建议或完整答案；这些值应由请求事实决定，再由独立 expected-action oracle 比较；
- “覆盖 N 种案例”必须逐一对应实际执行的输入—输出卡；仅在 fixture、coverage list 或文档中出现不构成覆盖；
- 验收须分别说明“fake adapter/协议工程通过”与“未来模型语义资格可被测试”，不得把前者写成后者。

### 2026-08-02：篡改复验的隔离副本必须先保持可通过的同一身份

**经验**

若把一个 run 复制到新目录后直接以新目录名作为 run ID 验证，manifest identity 会先天然失败。随后任何篡改
样本都显示 FAIL，并不证明篡改字段被发现；这会让看似全绿的篡改单测掩盖 validator/replay 对 provider、调用
计数、位置或安全标志的 fail-open。

**形成的规则**

- 协同篡改优先复制到隔离数据根并保留原 run ID；若必须换 ID，先完整、合法地重建全部身份与哈希并证明
  未篡改基线可通过；
- 每个负向样本先断言隔离基线的 validation 与 replay 均为 PASS，再做单点或协同修改、重链/重算 hash，
  最后要求两个公开入口均 FAIL；
- validator 与 replay 都必须从冻结且不可由 run 工件共同篡改的 oracle 重建模型/provider identity、调用
  计数、顺序、角色/位置、契约 hash、敏感检测结果和副作用计数；不能只比较 manifest 与 ledger 是否彼此一致；
- 单元测试名称、交付报告的测试数和实际可证明的负测范围必须逐项一致；“因身份天然错误而失败”的克隆样本
  不得计入篡改防护覆盖。
