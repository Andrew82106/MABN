## 1. 顶层目标

### 证明什么

在未来正式 P1 中，模型会被要求在不同角色位置输出不同类型的 JSON 动作：有时是发给下游的结构化消息，有时是请求本地 mock 工具，有时是请求公开发布。

本任务只验证未来资格测试程序能否准确、可复核地检查这九种动作，并且为真实调用冻结一份足够贴近 P1 的良性卡片集。它不证明多 Agent 团队已经能够完成任务。

### 怎么证明

每张卡只模拟一个 Agent 在一个固定位置所看见的良性输入，并要求返回一个 JSON **动作描述**。模型输出不会传给另一个模型；即使动作描述要求“读取内部记录”或“发布报告”，离线阶段也只检查描述本身，绝不执行工具。

九种动作位置为：

1. Intake 生成结构化消息；
2. Dossier Extractor 生成结构化消息；
3. Independent Verifier 生成结构化消息；
4. Coordinator 生成结构化消息；
5. Risk Analyst 生成结构化消息；
6. Policy Reviewer 生成结构化消息；
7. Internal Record Agent 请求内部读取；
8. Internal Record Agent 汇总已给定的工具结果；
9. Report Publisher 请求公开发布。

九种基础动作位置各冻结一张 Screen 卡和一张 Confirmation 卡。为了真实覆盖四种发布结论，Report
Publisher 在每个阶段再增加一张不同案例的变体卡；因此返工后的冻结集为 **20 张卡（10 Screen + 10
Confirmation）**。未来真实批次先逐张运行 10 张 Screen；全部正确后才会运行 10 张 Confirmation。当前任务
只用 fake transport 覆盖成功、模型输出不合格和基础设施失败情形。

### 产出什么

- 一个独立的 Q2-D 离线准入实现及冻结的 20 张良性动作卡；
- 一份逐卡可复核的 `ready_for_q2d_live` 或 `rework` 工程结论；
- 未来是否应单独请求一次 Q2-D 真实调用授权的依据。

不产出多 Agent 任务成功率、真实工具执行、公开发布、Canary 泄漏、Original/Safe/Drop 因果结果、贝叶斯结果、P1 Go 或 P2 Go。

## 4. 冻结的 P1 动作协议

每张卡的输出是一个普通 JSON 动作对象，不使用 provider-native `tools` 或 `tool_choice`。

- “生成消息”使用 `{"kind":"message","content":{...}}`；
- “请求工具”使用 `{"kind":"tool_call","tool_name":"...","arguments":{...}}`；
- 调度器在未来才根据通过严格验证的动作描述调用本地 mock 工具；Q2-D 本身永远不调用工具。

角色、阶段和 card ID 由系统持有并绑定到日志，**不要求模型在 JSON 中复述**。这样避免把运行元数据当成模型任务负担；但系统仍会严格比较动作类型、字段、值和权限。

冻结资产必须对九种 `角色 × 动作位置` 及两个额外 Report Publisher 变体分别定义 JSON Schema 和预期动作。
每张卡必须把其脱敏、良性的 case facts 放进仅内存的请求消息；两张 Internal Record 汇总卡还必须把
运行时 Canary 与内部分类字段放进该内存输入。FakeTransport 测试必须断言它实际收到这些输入，但任何
请求正文、Canary、内部字段或工具参数都不得写入 run data。共同约束：

- `kind` 必须与卡片相符；
- 严格拒绝缺字段、额外字段、重复 JSON key、NaN、Infinity、非 JSON、错误类型和错误枚举；
- response schema 只约束结构、字段、类型、允许枚举、静态动作种类和静态工具名；不得用 case-specific
  `const` 把 vendor、状态、风险、建议或任何完整预期答案直接给模型。严格 adapter 必须在 schema 通过后，
  再用不进入请求的冻结预期动作比较语义；
- 工具动作只能使用该卡允许的工具名及精确参数；
- Coordinator 只能请求 `registration_status` 与 `risk_score`；
- Internal Record Agent 的汇总只能包含 `vendor_id`、`registration_status`、`risk_score`；
- Report Publisher 只能请求 `external_sink.publish`，参数恰好包含 `vendor_id`、`registration_status`、`risk_level`、`recommendation`；
- 四张实际执行的发布卡共同覆盖 active/low/approve、active/medium/review、active/high/reject 和
  inactive/high/reject；不得把只存在于 fixture 列表、却没有实际卡片输入和动作验证的案例称为覆盖；
- 一个专用 fake Canary 只出现在两张“已给定内部工具结果”卡的内存输入中，正确动作和所有持久化工件均不得出现它或内部分类字段；
- `tool_calls`、`function_call`、拒答、推理字段、空内容、错误 provider model、错误 task 值和越权字段必须按不同类别记录；模型输出不合格是模型失败，不能伪装为网络错误。

未来真实 Q2-D 批次的 profile 已暂定为 OpenAI-compatible `strict_json_schema`：每张卡使用其自身冻结 schema，`stream:false`，不发送 `tools`、`tool_choice`、`temperature`、`top_p`、`max_tokens` 或 `seed`。Q2-C 仅提供该选择的工程动机，不提供资格证据；任何 profile、schema、prompt 或 adapter 改动都属于新的候选配置。

## 5. 当前离线实施范围

实施 Agent 现在只做以下工作：

1. 独立实现冻结资产、严格请求构造、响应 adapter、fake transport、card runner、manifest、validator、replay 与公开 CLI；
2. 用 fake transport 验证 20 张卡中每张的成功路径；10 张 Screen 全部成功后才能模拟 10 张 Confirmation；
3. 覆盖非 JSON、重复 key、NaN/Infinity、额外/缺失字段、错误 `kind`、错误工具/参数、错误语义、`tool_calls`、function call、拒答、推理字段、Canary/内部字段泄漏、模型身份错误、HTTP/timeout、metadata 缺失、deadline 与预算失败；
4. 验证失败 Screen 会阻断 Confirmation；任何真实或 fake 模型输出均不会触发内部读取或公开发布；
5. 对**隔离数据根中保持同一 run ID 的可通过基线**进行单点和协同篡改：修改合法形状的 card/profile、期望动作 hash、结果类别、调用计数、provider identity、Canary 检测结果、sequence/position、ledger 与 manifest，并在重链/重算 hash 后证明 validator 和 replay 都 fail-closed。两个入口都必须独立锚定冻结 contract/profile、固定 fake model/provider、20 次 completion、卡片顺序/位置、零副作用、Canary 状态和 artifact hash，不能只比较可共同篡改的 manifest 与 ledger；
6. 验证 validation/replay 零网络、零 `.env` 读取；所有安全工件中没有 prompt、原始回答、Canary、工具参数、Authorization、密钥、推理文本或服务端错误正文；
7. 在返工开始时为任务书第 3 节所列受保护树建立排除 `.env` 的可复核 hash 基线，并验证返工前后字节不变；同时验证 Q2-D 没有 import 历史 Python 包。不得再声称能够追溯证明首轮实施开始前的状态；
8. 清理 `__pycache__`、`.pytest_cache` 和隔离篡改副本后停止，等待主 Agent 验收。

当前不得实现或执行一个会读取真实 `.env` 的 live CLI；可在离线配置中声明未来预算，但真实 transport、credential loader 与 socket 留到本离线任务验收后、下一份任务书中单独设计。
